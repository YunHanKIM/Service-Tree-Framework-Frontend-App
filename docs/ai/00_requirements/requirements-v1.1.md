# QR 물품 대여 앱 기획 및 요구사항 정의서

포트폴리오용 React Native 프로젝트  |  기획안 1.1  |  2026년 9월 28일  |  목표 직무: 프론트엔드

추천 프로젝트는 소규모 동아리나 스터디가 공동 물품을 등록하고 QR 코드로 대여와 반납을 기록하는 모바일 앱이다. 사용자에게는 물품의 현재 상태와 자신의 대여 내역을 명확하게 보여주고, 관리자에게는 재고와 대여 이력을 제공한다. 이 문서는 첫 버전의 범위와 구현 판단 기준을 정한다. 일정은 1인 개발을 가정한 추정치다.

목표 직무가 프론트엔드이므로 서버는 Supabase(관리형 백엔드)에 맡기고, 개발 시간은 앱의 상태 관리·예외 처리·접근성·테스트 품질에 집중한다. 개발은 TDD(테스트 우선 개발)로 진행한다.

## 1 프로젝트 개요

| 항목 | 정의 |
| --- | --- |
| 가칭 | 빌림 — QR 기반 공동 물품 대여 관리 |
| 대상 | 동아리·스터디·소규모 공유 공간의 회원과 관리자 |
| 해결할 문제 | 물품이 누구에게 있는지 구두·채팅으로 확인해야 하며, 반납 누락과 중복 대여가 생긴다. |
| 핵심 가치 | 스캔 → 대여 가능 확인 → 신청 → 관리자 승인 → 반납 요청 → 반납 확인까지 상태를 추적한다. |
| 포트폴리오 관점 | 카메라 권한·QR 인식, 서버 상태 관리(캐시·재시도·무효화), 로딩·빈 목록·오류·오프라인 상태 처리, 접근성, TDD로 쌓은 테스트와 커밋 이력, 실기기 검증 |

운영 가정: 하나의 데모 조직에 회원과 관리자 역할을 둔다. 로그인은 이메일·비밀번호 방식이다. QR에는 비밀 정보나 사용자 정보 없이 정해진 형식의 물품 식별자(uuid)만 담는다.

## 2 목표와 성공 기준

- 회원이 물품을 찾고 대여 신청을 완료하기까지의 주요 흐름을 목록 → 상세 → 신청 확인, 3개 화면 안에서 끝낸다.
- 두 관리자가 같은 물품의 서로 다른 신청을 동시에 승인해도 확정되는 대여는 한 건만 허용하고, 실패한 쪽 앱은 이유를 보여주며 목록을 갱신한다.
- 핵심 순수 로직(QR 해석, 상태 계산, 날짜 검증)은 테스트를 먼저 작성하고, 해당 모듈의 분기 커버리지를 90% 이상으로 한다.
- 대여·반납 정상 흐름, 카메라 권한 거부, 잘못된 QR, 중복 신청, 동시 승인 실패, 네트워크 단절을 재현하고 기대 결과를 기록한다.
- README에 두 역할의 데모 계정, 설치 가능한 빌드 링크, 시나리오별 시연 영상, 인쇄용 QR, 설계 선택과 실패 처리 사례를 남긴다. 위 수치는 제품의 실제 성과가 아닌 개발 완료 기준이다.

## 3 사용자와 핵심 시나리오

| 역할 | 할 수 있는 일 | 제한 |
| --- | --- | --- |
| 회원 | 물품 검색, QR 스캔, 대여 신청·취소, 본인 신청·대여 내역 확인, 반납 요청 | 다른 회원의 대여 상세, 관리자 기능, 본인 역할 변경 불가 |
| 관리자 | 물품 등록·수정·사용 중지, QR 확인, 신청 승인·거절, 반납 확인, 이력 조회 | 활성 대여가 있는 물품은 사용 중지·삭제 불가 |

대표 시나리오: 관리자가 빔 프로젝터를 등록하고 QR을 붙인다. 회원이 앱에서 코드를 스캔해 물품 상세와 상태를 확인하고, 반납 예정일을 골라 대여를 신청한다. 관리자가 승인하면 물품이 대여 중이 되고, 같은 물품의 다른 대기 신청은 자동으로 거절된다. 회원이 반납을 요청하면 관리자가 실물을 확인한 뒤 반납 완료로 처리하고, 물품은 다시 대여 가능이 된다.

## 4 범위와 제외 항목

| 구분 | 포함 범위 |
| --- | --- |
| 첫 버전 필수 | 이메일 인증, 회원·관리자 권한, 물품 목록·검색·상세, QR 스캔, 대여 신청·취소·승인·거절, 반납 요청·확인, 본인 이력, 로딩·빈 목록·오류·오프라인 화면 |
| 첫 버전 선택 | 물품 사진 1장, 관리자 QR 이미지 공유·인쇄용 PDF, 간단한 기한 경과 표시 |
| 후속 버전 | 푸시 알림, 여러 조직, 오프라인 작성 후 동기화, 예약 대기열, 파손 신고, 관리자 통계 |

범위 결정: 승인 권한과 재고 확정이 서버에 있어야 하므로 오프라인에서는 대여를 확정하지 않는다. 인터넷이 없을 때는 캐시된 화면을 보여줄 수 있지만, 신청과 상태 변경은 막고 재시도를 안내한다.

## 5 기능 요구사항

| ID | 우선 | 기능과 수용 기준 |
| --- | --- | --- |
| FR01 | 필수 | 사용자는 이메일로 가입·로그인·로그아웃하고 비밀번호를 재설정한다. 로그인하지 않으면 보호 화면 대신 로그인 화면을 본다. 인증 메일 링크는 앱 딥링크로 받는다. |
| FR02 | 필수 | 회원은 이름으로 물품을 검색하고 상태(대여 가능·대여 중·사용 중지)로 필터링한다. 본인의 대기 신청이 있는 물품에는 "내 신청 대기" 배지를 표시한다. 결과가 없으면 빈 상태를 본다. |
| FR03 | 필수 | 카메라 권한에 동의하고 QR을 스캔하면 해당 물품 상세로 이동한다. 권한을 거부하면 설정 이동 안내와 목록 검색 경로를 제공한다. |
| FR04 | 필수 | 형식이 `billim://item/<uuid>`가 아니거나, 미등록이거나, 손상된 QR은 원인별 오류를 표시하고 재스캔할 수 있게 한다. 같은 QR이 연속으로 감지돼도 이동과 요청은 한 번만 일어난다. |
| FR05 | 필수 | 회원은 반납 예정일을 골라 대여를 신청한다. 과거 날짜, 같은 물품에 대한 본인의 중복 대기 신청, 대여 중이거나 사용 중지된 물품은 앱에서 먼저 막고 서버에서도 거부한다. |
| FR06 | 필수 | 관리자는 대기 중인 신청을 승인하거나 사유와 함께 거절한다. 승인은 서버 함수 하나에서 원자적으로 처리한다(활성 대여 없음 검증 → 대여 생성 → 다른 대기 신청 자동 거절). 승인이 충돌하면 앱은 이유를 보여주고 목록을 갱신한다. |
| FR07 | 필수 | 대여 중인 회원은 반납을 요청한다. 관리자가 확인해야 물품이 다시 대여 가능이 된다. |
| FR08 | 필수 | 회원은 본인의 신청·대여 기록을, 관리자는 조직 전체 기록(처리자·처리 시각 포함)을 확인한다. 권한은 서버 데이터 정책(RLS)으로 제한한다. |
| FR09 | 필수 | 관리자는 물품의 이름·설명·사진을 등록·수정하고 사용 여부를 바꾸며, 물품별 QR을 확인한다. 대여 상태는 직접 수정하지 않는다. |
| FR10 | 필수 | 네트워크 오류가 나면 진행 표시를 끝내고 실패 이유와 재시도 버튼을 보여준다. 처리 중에는 버튼을 비활성화해 두 번 탭해도 요청이 한 번만 가게 한다. |
| FR11 | 필수 | 회원은 본인의 대기 신청을 취소한다. 이미 처리된 신청은 취소할 수 없고, 앱은 최신 상태를 다시 불러와 보여준다. |

## 6 상태 규칙과 데이터

**상태 원칙**: 물품의 대여 상태는 따로 저장하지 않고 `loans`에서 계산한다. 같은 사실을 두 곳에 저장하면 서로 어긋나기 때문이다.

| 대상 | 상태 | 규칙 |
| --- | --- | --- |
| 물품 표시 상태 | 사용 중지 > 대여 중 > 대여 가능 | `is_active = false`면 사용 중지, 반납 완료 전 대여가 있으면 대여 중, 그 외는 대여 가능 |
| 신청 (requests) | 대기 → 승인 / 거절 / 취소 | 대기 신청은 물품을 선점하지 않는다. 최초 승인만 대여를 확정하고, 같은 트랜잭션에서 나머지 대기 신청을 자동 거절한다. 취소는 대기 상태에서만 할 수 있다. |
| 대여 (loans) | 활성 → 반납 요청 → 반납 완료 | 반납 요청 상태도 물품은 대여 중으로 본다. 반납 완료는 관리자만 처리한다. |

| 개체 | 주요 필드 | 핵심 제약 |
| --- | --- | --- |
| profiles | id(= auth 사용자 id), email, display_name, role, organization_id | 회원은 본인 프로필만 조회. `role`·`organization_id`는 본인이 수정할 수 없음 |
| items | id(uuid), organization_id, name, description, image_path, is_active, created_at | QR에는 `billim://item/<id>`만 인코딩 |
| requests | id, item_id, user_id, due_date, status, reject_reason, processed_by, processed_at, created_at | `status = 'pending'` 조건의 (item_id, user_id) 부분 유니크 인덱스 |
| loans | id, item_id, user_id, request_id, due_date, borrowed_at, return_requested_at, returned_at, return_confirmed_by, status | `status in ('active','return_requested')` 조건의 item_id 부분 유니크 인덱스 |

- 날짜: `due_date`는 시각이 아닌 날짜(date) 타입이며 한국 시간(Asia/Seoul)을 기준으로 한다. 오늘 날짜 신청은 허용한다.
- 상태 변경: 승인·거절·취소·반납 요청·반납 확인은 앱에서 테이블을 직접 update하지 않고, 역할을 검사하는 Postgres 함수(RPC)로만 처리한다.

## 7 화면 구성과 이동

| 화면 | 주요 내용 | 진입 |
| --- | --- | --- |
| 로그인·가입 | 이메일·비밀번호 입력, 오류, 비밀번호 재설정 | 최초 실행 또는 로그아웃 |
| 물품 목록 | 검색, 상태 필터, 카드, 스캔 버튼, 당겨서 새로고침 | 로그인 후 기본 화면 |
| QR 스캔 | 카메라 미리보기, 권한 안내, 원인별 오류, 재스캔 | 목록의 스캔 버튼 |
| 물품 상세 | 사진, 상태, 설명, 반납 예정일 선택, 신청 버튼 | 목록 또는 스캔 결과 |
| 내 대여 | 신청 상태, 신청 취소, 반납 요청, 기한 경과 표시 | 하단 탭 또는 신청 완료 후 |
| 관리자 | 물품 등록·수정, 신청 처리, 반납 확인, 이력 | 관리자 계정의 하단 탭 |
| 공통 상태 | 로딩, 빈 목록, 오류와 재시도, 오프라인 배너 | 모든 데이터 화면 |

기본 이동: 로그인 → 목록 → 상세(날짜 선택·신청) → 내 대여. 스캔은 목록 → QR 스캔 → 상세로 합류한다. 관리자 이동은 관리자 탭 → 신청 상세 → 승인 또는 거절이다.

## 8 비기능 요구사항과 검증

| 영역 | 요구와 확인 방법 |
| --- | --- |
| 보안 | 역할 검사는 화면 표시뿐 아니라 RLS와 RPC 함수에서도 수행한다. 회원이 본인 `role`을 바꾸려는 요청이 거부되는지 확인한다. QR에 인증 정보·개인정보를 넣지 않는다. |
| 접근성 | 모든 버튼에 `accessibilityLabel`을 제공하고, 상태는 색과 함께 아이콘·텍스트로도 표시한다. 큰 글꼴과 화면 읽기(TalkBack·VoiceOver)를 실기기에서 확인한다. |
| 성능 | 목록 최초 로딩과 검색 응답 시간을 측정하고 FlatList 최적화 전후를 비교해 README에 기기·네트워크 조건과 함께 기록한다. 목표치는 실측 후 정한다. |
| 호환성 | Android 실기기 1대와 iOS 시뮬레이터 또는 실기기에서 주요 흐름을 확인한다. 카메라 스캔은 실제 기기에서 검증한다. |
| 안정성 | 로딩·빈 목록·권한 거부·네트워크 단절·서버 오류·동시 승인 실패를 각각 재현하고, 가능한 항목은 자동 테스트로 남긴다. |

## 9 권장 기술과 선택 근거

| 구성 | 제안 | 이유와 유의점 |
| --- | --- | --- |
| 앱 | React Native + Expo + TypeScript | JavaScript·React 경험을 살리고 모바일 빌드와 기기 API 접근을 단순화한다. |
| 이동·스캔 | Expo Router + expo-camera | 파일 기반 화면 이동과 CameraView의 QR 인식을 사용한다. 인증 메일 딥링크 처리도 포함한다. |
| 서버 상태 | TanStack Query | 캐싱·재시도·무효화를 처리한다. 승인·반납은 결과가 확정된 뒤에만 화면을 바꾸고 낙관적 업데이트는 쓰지 않는다. |
| 백엔드 | Supabase Auth + Postgres + Storage | 인증·관계형 데이터·사진 저장을 맡긴다. RLS와 상태 변경 RPC는 직접 작성한다. |
| 단위·컴포넌트 테스트 | Jest(`jest-expo`) + React Native Testing Library | TDD의 주 도구. 순수 로직·훅·화면 동작을 테스트한다. |
| 네트워크 모킹 | MSW 또는 Supabase 클라이언트 모킹 | 오류·지연·충돌 응답을 재현한다. |
| E2E | Maestro | 주요 흐름의 수용 테스트. 카메라 스캔은 실기기에서 수동으로 확인한다. |
| 배포 | EAS Build | 면접관이 설치할 수 있는 Android 빌드 링크를 제공한다. |

기술 선택은 2026년 9월 28일 기준의 제안이며, 구현을 시작할 때 호환 버전과 요금·제약을 다시 확인한다. 가장 어려운 부분은 동시 승인을 서버에서 안전하게 처리하는 일이다. 이는 DB 제약과 RPC 함수로 막고, 앱에서는 충돌 응답을 받았을 때의 동작을 테스트하는 데 집중한다.

## 10 개발 단계와 산출물

모든 구현 단계는 "실패하는 테스트 → 통과하는 구현 → 정리" 순서로 진행한다.

| 순서 | 작업 | 완료 산출물 |
| --- | --- | --- |
| 1 | 기획 확정 및 예외 정책 결정 | 이 문서의 범위와 상태 규칙 확정 |
| 2 | 화면 흐름 및 저충실도 와이어프레임 | 회원·관리자 핵심 화면, 공통 상태 화면, 권한 거부 화면 |
| 3 | 데이터 모델·RLS·RPC 설계 | 테이블, 부분 유니크 인덱스, 권한 규칙, 승인 함수, 시드 데이터 |
| 4 | 프로젝트 환경·테스트 환경·인증 | Jest·RNTL 설정과 첫 테스트 통과, 역할별 진입 |
| 5 | 물품 목록·상세·QR | QR 해석·상태 계산 테스트 우선, 검색·스캔 정상 및 오류 흐름 |
| 6 | 신청·취소·승인·반납 | 날짜 검증·중복 탭·충돌 응답 테스트 우선, 서버 상태 전이 확인 |
| 7 | 품질 확인과 포트폴리오 정리 | Maestro 시나리오, 실기기 테스트, 접근성 점검, 시연 영상, EAS 빌드, README, 설계 회고 |

일정 추정: 주 10~12시간 기준 6~8주. 환경·테스트 설정·인증 1~2주, 목록·스캔 1.5~2주, 신청·승인·반납 2~2.5주, 품질 확인·시연 문서 1~1.5주로 배분한다. 테스트 도구 학습과 기기 확보 상황에 따라 달라질 수 있다.

## 11 테스트 전략 (TDD)

**원칙**: 동작을 테스트한다. 구현 세부(내부 state 값, 호출 순서)가 아니라 사용자가 보는 결과와 함수의 입출력을 검증한다.

| 대상 | 먼저 작성할 테스트 예 | 관련 요구 |
| --- | --- | --- |
| `parseItemQr(raw)` | 정상 형식은 uuid 반환, 다른 앱의 QR·빈 문자열·잘못된 uuid는 원인별 오류 | FR04 |
| `deriveItemStatus(item, loans)` | 사용 중지 우선, 반납 요청 중이면 대여 중, 반납 완료만 있으면 대여 가능 | 6장 |
| `validateDueDate(date, today)` | 과거 거부, 오늘 허용, 한국 시간 자정 경계값 | FR05 |
| 스캔 디바운스 훅 | 같은 값이 연속으로 들어와도 콜백 1회 | FR04 |
| 신청 버튼 | 탭하면 비활성화, 두 번 탭해도 요청 1회, 실패하면 재시도 버튼 | FR10 |
| 권한 거부 화면 | 설정 안내와 목록 검색 경로 표시 | FR03 |
| 승인 충돌 처리 | 충돌 응답이면 안내 메시지 표시 후 목록 다시 조회 | FR06 |
| 신청 취소 | 이미 처리된 신청이면 오류 표시 후 최신 상태 표시 | FR11 |

- **TDD로 다루지 않는 것**: 실제 카메라 인식은 실기기 수동 체크리스트로, RLS·동시 승인은 SQL 검증 스크립트(두 세션에서 동시에 승인)로 확인하고 결과를 README에 남긴다.
- **커밋 규칙**: `test:`(실패하는 테스트) → `feat:`(통과시키는 구현) → `refactor:` 순으로 나눠 TDD 과정이 git 이력에 남게 한다.
- **완료 기준**: 순수 로직 모듈의 분기 커버리지 90% 이상. 화면은 커버리지 수치보다 5장 수용 기준을 모두 테스트했는지로 판단한다.

## 12 구현 전 확정할 결정

- 데모 조직에 가입한 사용자에게 회원 역할을 자동 부여할지, 관리자가 초대할지 정한다. 현재 문서는 자동 회원 부여를 가정하며, 관리자 계정은 시드 데이터로 만든다.
- 대여 기간 상한(예: 최대 14일)을 둘지 정한다. 첫 버전은 상한 없이 기한 경과 표시만 제안한다.
- iOS 실기기와 Android 실기기를 모두 사용할 수 있는지 확인한다. 부족하면 실제 검증 범위를 포트폴리오에 정확히 적는다.
- 네트워크 모킹을 MSW로 할지, Supabase 클라이언트를 감싼 API 계층을 모킹할지 정한다. 후자가 설정이 단순하다.
